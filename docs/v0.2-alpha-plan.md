# v0.2 alpha 公开规划

v0.1 的目标是公开一条干净的主链路。v0.2 alpha 的目标不是把维护者工作区完整开源，而是把已经稳定的续接和检查能力产品化成公开文档、公开 CLI 和公开示例。

## 主题

**可恢复的 AI coding session**：当一次需求跨越多次对话或多天时间，用户可以通过明确的 state、handover 和 recall 入口恢复上下文。

## 建议发布切片

| 优先级 | 能力 | 成熟度依据 | 当前状态 |
|--------|------|------------|----------|
| P0 | `state` + `recall` 单仓版 | 开发版已有实现和专门测试覆盖；不依赖项目注册表时边界最干净 | **已纳入** first slice：单仓 state/recall、最小 `.zimaflow-state.yaml` schema、基础测试 |
| P1 | `release-check` | 开发版已有实现和测试；默认只读，不 deploy、不读取发布凭证 | **已纳入**：发布前软 checklist、四问、secrets 只报 `path:line` |
| P1 | `context-check` | 开发版已有实现和测试；与已公开的 legacy onboarding / context index 配套 | **已纳入**：只读检查 context index 的 baseline / workflow 指针是否仍存在 |
| P2 | `drift-check` | 开发版已有实现；公开前需要补足边界测试 | 补测试后再纳入，只报告 hash 漂移，不自动改写 |
| P3 | Guardrail Catalog | 适合先文档化，再决定是否提供机器可读配置 | 先文档，不默认阻断，不绑定单一 agent runtime |

> 口径说明：本表描述的是**规划切片**，不是当前公开 CLI 的命令清单。截至当前公开版，`bin/zimaflow` 实际提供的命令是 `close`、`state`（含 `init` / `update`）、`recall`、`context-check`、`release-check`、`install-hooks`；`drift-check` **还不能运行**。以 `bin/zimaflow --help` 为准，命令说明见 [CLI 速查](cli-reference.md)。

`recall --all` 和 `recall --project` 暂不进入第一批公开切片，因为它们需要项目注册表约定。v0.2 alpha 先保留单仓恢复路径，避免把维护者工作区布局变成开源用户的隐式依赖。

## 暂不纳入

| 内容 | 原因 |
|------|------|
| `proto-review` 自动原型评审 | 需要公开模板、示例和资产边界后再开放 |
| 完整项目初始化器 | 需要避免隐式修改用户项目、agent 配置或项目注册表 |
| 知识使用账本原始数据 | 属于个人或项目使用证据，不适合公开原文 |
| 开发版 Roadmap 原文 | 含内部评估、未稳定取舍和维护者上下文 |
| 真实项目经验库 | 必须抽象成通用 lesson 后再公开 |
| 默认 hard hooks | 可能影响用户工作流，只能作为显式可选能力 |

## 文档拆分

- `docs/session-continuity.md`：解释 state、handover、recall 和 context index 如何配合。
- `docs/guardrails.md`：解释公开护栏、软 gate 和 hard hook 边界。
- `docs/open-source-boundary.md`：持续维护什么能进公开仓，什么必须等示例和脱敏完成。
- `docs/workflow-overview.md`：保留 v0.1 主链路，同时补充续接视角。

## 发布前检查

- 不出现本机绝对路径、真实项目名、真实公司名、密钥或私有服务。
- README 不承诺尚未合并到开源仓的命令已经可用。
- CLI 文档必须和 `bin/zimaflow --help` 对齐。
- 后续规划使用方向性措辞，不把维护者内部版本号当作公开版本号。
