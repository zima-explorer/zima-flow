## 为什么只是候选

`learn` 的规则是：AI 只输出候选，**用户确认后才写入** `references/lessons-common.md` 或项目 `lessons.md`。本文件就是那份候选清单——它没有、也不应该自动进入任何公共经验库。

这本身是要展示给读者的产品行为：经验沉淀是有人把关的动作，不是 AI 的副作用。

## 候选 1：过滤类功能必须有负向断言

- **主题**：给功能加筛选 / 过滤能力时，测试必须包含「结果中**不含**另一类」的负向断言。
- **触发证据**：本轮场景 1、2 若只断言「目标项存在」，那么即使 `--status` 被完全忽略、两个分区照常全渲染，断言依然会通过。测试会绿，功能是坏的。
- **可复现的判据**：把过滤条件改成恒真，测试必须变红。变不红说明断言选错了。
- **建议级别**：lesson
- **建议写入**：通用经验库（测试设计条目）
- **状态**：候选，未写入

## 候选 2：入口层未透传已有判定逻辑是常见缺口

- **主题**：动手实现前，先确认底层判定逻辑是否已经存在——缺的往往是入口开关，不是能力本身。
- **触发证据**：本轮需求看起来是「新增状态筛选」，但 `cmd_list` 早就按 done 位分两区渲染，判定逻辑已经存在。真正缺的只是让用户选择渲染哪一区的入口。先查再写，把一个「实现过滤器」的活变成了「加一个开关」。
- **反面代价**：不先查就动手，容易在入口层另写一套状态判定，与既有渲染逻辑并存，日后两处不一致。
- **建议级别**：pattern 候选
- **建议写入**：通用经验库（实现前置检查条目）
- **状态**：候选，未写入
