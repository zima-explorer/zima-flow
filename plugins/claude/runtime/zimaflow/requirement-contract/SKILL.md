# Requirement Contract — 需求契约

## 职责

在需求进入路线决策、原型评审、任务拆解或 OpenSpec 之前，确保它有一份写下来的、已确认的"需求契约"。

区分两件事：

- **必经的**：需求契约本身（brief 或 PRD 二选一）。
- **不必经的**：完整 PRD。大多数个人项目、小修小补、低风险需求，一份 5-10 行的 brief 就够，不需要走完整 PRD 的分段生成流程。

## 两种模式

| 模式 | 适用场景 | 产物形态 |
|------|---------|---------|
| `brief`（默认） | 个人项目、小修小补、老项目叠加功能、低风险低复杂度需求 | 5-10 行：意图锁、目标、范围、不做什么、验收标准、风险/待确认 |
| `prd`（复杂模式） | 产品型界面、多状态 UI、多角色协作、涉及权限/计费/敏感信息、团队协作/公司多环境项目、用户明确要求 PRD | 分模块生成，逐段人工确认：背景与目标 → 用户/场景 → 功能范围 P0/P1/P2 → 业务规则与边界 → 验收标准 |

模式选择由调用方（通常是 `sdd-router`）根据已有的项目协作模式、需求形态、复杂度/风险判断结果建议，用户可以覆盖。拿不准时，先建议 `brief`，需要时可以从 brief 升级为 PRD，不强制一步到位选重的。

### 与三档路由的对应

| 路由档位 | 契约要求 |
|---------|---------|
| `quick` | **不强制契约**。口头确认目的、范围、完成标准即可，不落盘。用户要求留痕时可写最小字段 brief |
| `standard` | **最小字段 brief 起步**（见下），按需补全，不预先写满 |
| `full` | 完整 brief 或 PRD，必须"已确认"才放行下游 |

**不要对小需求生成过重契约**：如果一个需求的契约文档明显长于它的实现，说明档位判断或字段取舍出了问题，应回到 `sdd-router` 重新定档，而不是继续把契约写完。

## brief 最小字段

`standard` 档和"用户要求留痕的 quick"从这四个字段起步，**其余字段按需再加，不预先写满**：

```markdown
# <需求名> · 需求 Brief

> 状态：待确认 ｜ 日期：YYYY-MM-DD

- **意图锁**：{一句话，本轮为什么做}
- **范围**：{做什么，边界在哪}
- **不做什么**：{明确排除，避免蔓延}
- **怎么算做完**：{一句验收；有明确输入输出时才展开成 Given/When/Then}
```

四个字段的取舍理由：

- **意图锁**保留——它是防范围漂移的锚点，也是三档中唯一贯穿的字段，去掉它下游就没有对照基准。
- **范围 / 不做什么**保留——小需求最常见的失败不是做错，而是越做越多。
- **怎么算做完**保留——它是 verification 的最低依据，quick 档也要留验证方式。
- **目标**在最小字段中与意图锁合并，不单列（小需求里两者常常是同一句话）。
- **假设与默认值 / 风险待确认**按需添加：只有当 AI 确实做了假设、或存在需要用户拍板的不确定项时才写；无则整段省略，不写"无"占位。

升级路径：最小字段 brief 可以直接扩写成完整 brief（补目标、假设与默认值、风险/待确认），完整 brief 可以直接作为 PRD 的输入。**已写的内容不作废、不重写。**

## 输入优先级

1. **会议纪要 / 需求沟通对话记录**（优先）——信息纯净、只记双向确认后的结论
2. **零散文字描述**——用户随手写的几句话、聊天记录片段
3. **用户口头补充**——AI 主动追问缺口

**不要求用户先写一份 BRD 再喂给你**。BRD 式输入噪音多（背景目标混杂、方案越界、共识模糊），是这个 Skill 明确不采用的输入方式。

如果用户已经有 PRD、brief 或外部需求文档链接，直接引用它、不重新起草；只需要向用户确认"这份还是当前有效的吗"，确认后即可视为已确认契约，跳过生成步骤。

## brief 模式

### 产物结构

```markdown
# <需求名> · 需求 Brief

> 状态：草稿 / 待确认 / 已确认
> 日期：YYYY-MM-DD
> 输入来源：会议纪要 / 对话描述 / 口头补充

- **目标**：{一句话，这个需求要解决什么}
- **意图锁**：{一句话，这一轮做这件事的核心目的是什么；后续路线、任务和 OpenSpec 必须对照它}
- **范围**：{本轮做什么，边界在哪}
- **不做什么**：{明确排除的内容，避免范围蔓延}
- **验收标准**：{优先写成 Given / When / Then，见下方规则；简单场景可写一句"怎么算做完"}
- **假设与默认值**：{信息不足、追问已达上限时，AI 假设的默认取值，需用户事后 review；无则写"无"}
- **风险/待确认**：{不确定的点，需要谁来拍板}
```

控制在 5-10 行（不含 GWT 展开），不展开成完整 PRD 的章节结构。如果发现内容自然膨胀超出这个量级，说明这个需求可能需要升级到 `prd` 模式，向用户提出确认。

## 意图锁：防范围漂移

每份已确认需求契约都必须包含 `意图锁`。它不是更长的目标描述，而是一句稳定的"本轮为什么做"：

```markdown
- **意图锁**：本轮只解决 {核心问题}，让 {对象/用户/系统} 能够 {关键结果}。
```

规则：

- 意图锁必须足够短，能被后续 Decision、tasks、OpenSpec 三件套引用和对照。
- 意图锁不替代目标、范围、不做什么和验收标准；它只负责防止后续规划偏离最初目的。
- 如果用户后续扩大/缩小范围，先判断是否仍符合意图锁；不符合时回到本契约修订并重新确认。
- 轻量模式也保留意图锁，但只作为对照提醒，不增加额外流程。

**三档中的写法轻重不同，但都要有**：

| 档位 | 意图锁写法 |
|------|-----------|
| `quick` | **口头一句话即可**，不必落盘；作用是让实现者和用户对"这轮到底要干什么"有共识 |
| `standard` | brief 中一行，作为 task-planning 的对照基准 |
| `full` | 契约中正式记录，下游 Decision / tasks / OpenSpec 三件套必须显式引用或复述 |

quick 档不落盘不等于可以不想清楚：如果一句话都说不清本轮目的，那说明需求本身还没成型，应该先澄清而不是直接动手。
- 不新建 `execution-contract.md`，不做自动回退；意图锁是软约束和人工确认锚点。

### 输出位置

```text
<docs_dir>/Requirements/YYYY-MM-DD · <需求名> brief.md
```

## 验收标准：优先 Given / When / Then

验收标准优先用 BDD 三段式写，让后续 spec-compliance-check 和 TDD 能直接派生测试矩阵，不用把自由文字二次翻译成测试。

格式：

```markdown
- **验收标准**：
  - Given {前置状态/上下文}，When {触发动作}，Then {可观察的预期结果}
  - Given {前置}，When {动作}，Then {预期}
  - （异常/边界）Given {异常前置}，When {动作}，Then {错误处理预期}
```

规则：

- 每条 AC 是一个可独立验证的行为，Then 必须是可观察、可断言的结果，不写"体验更好"这类不可测表述。
- 尽量覆盖正常路径 + 至少一个异常/边界场景。
- 纯配置、纯文案、纯样式等确实无行为可断言的小改动，可以退回一句话验收标准，但要说明"无可派生测试场景"。
- brief 和 prd 模式的验收标准都适用本规则。

## 反问上限与假设默认值

需求信息不足时可以追问，但不允许无限追问，避免 flow-kit 记录过的"十几轮反问、每轮都差不多"的死循环。

规则：

- **最多反问 2 轮**。每轮把关键缺口一次问清，不要挤牙膏式一次只问一个。
- 到第 3 轮仍有缺口时，**不再追问**，改为对剩余缺口取合理默认值，写进契约的"假设与默认值"段落，交由用户事后 review 覆盖。
- 用户给出 escape 信号（如"够了"、"按你想的来"、"你看着办"、"先这样"）时，**立即停止追问**，把未确认项写入"假设与默认值"，进入待确认状态。
- 假设默认值必须显式标注为 AI 假设，不能伪装成用户已确认的结论。
- 反问只针对影响范围、验收标准、边界的关键缺口；无关紧要的细节直接取默认值，不占用反问轮次。

## 决策证据边界（ZF-GR-005）

读取 `references/guardrails.yaml` 中的 `ZF-GR-005 analogy_for_search_evidence_for_decision`。需求契约是下游规划的确认输入，因此它必须比普通讨论更严格地区分"证据"和"推断"。

核心规则：**联想用于搜索，引用用于决策**。

起草 brief / PRD 时，范围、验收标准、不做什么、业务规则必须标注或能追溯到决策证据：

| 结论类型 | 可接受决策证据 |
|---------|----------------|
| 目标 / 范围 | 用户原话、已有 PRD/brief、会议纪要、已确认 Decision |
| 不做什么 | 用户排除项、路线决策、风险边界、明确的本轮意图锁 |
| 验收标准 | 用户确认的可观察结果、已有测试/行为、设计标注、PRD 原文 |
| 业务规则 | PRD/文档原文、用户确认、代码事实；没有证据时只能写入待确认 |
| AI 默认值 | 只能进入"假设与默认值"，等待用户 review |

规则：

- 可以用领域联想生成追问、搜索词或候选解释，但不能直接写入"范围"或"验收标准"。
- AI 假设不能进入已确认范围；确认前只能保留在"假设与默认值"或"待确认问题"。
- 用户确认后，可以把假设转为已确认结论，并保留输入来源为"用户确认"。
- 如果无法给关键范围项找到决策证据，契约状态最多是"待确认"，不能标为"已确认"。

brief 模式建议在"风险/待确认"或"假设与默认值"中记录：

```markdown
- **决策证据**：用户原话 / 既有 PRD / 代码事实 / 设计标注 / AI 假设（待确认）
```

## prd 模式

### 分段生成规则

**不要一次性生成整份 PRD。** 按以下顺序逐段生成，每段生成后停下来，等用户确认这一段，确认后才生成下一段：

1. 背景与目标
2. 用户 / 场景
3. 功能范围（P0 / P1 / P2 分级）
4. 业务规则与边界
5. 验收标准

每段生成前，先说明这段准备写什么、依据是什么（来自会议纪要哪部分、还是 AI 推断），推断内容必须显式标注。

### 上下文投喂原则

不要把项目所有历史文档全量塞进上下文。优先给精炼摘要：本轮相关的 `Decisions/` 结论、同类历史需求的关键结论、相关代码模块索引（如果有）。全量堆料容易导致内容编造或跑题，只投喂和本次需求直接相关的精炼材料。

### 产物结构

```markdown
# <需求名> · PRD

> 状态：草稿 / 待确认 / 已确认
> 日期：YYYY-MM-DD
> 输入来源：会议纪要 / 对话描述 / 口头补充
> 生成方式：分段生成，逐段人工确认

## 一、背景与目标

## 二、用户 / 场景

## 三、功能范围

### P0（必须）

### P1（重要）

### P2（可选）

## 四、业务规则与边界

## 五、验收标准
（优先 Given / When / Then 三段式，见"验收标准：优先 Given / When / Then"节）

## 六、意图锁
（一句话说明这一轮做这件事的核心目的；后续 Decision、tasks、OpenSpec 必须对照）

## 七、假设与默认值
（反问达上限或用户 escape 后，AI 取的默认取值，需用户事后 review；无则写"无"）

## 八、待确认问题
```

### 输出位置

```text
<docs_dir>/PRDs/YYYY-MM-DD · <需求名> PRD.md
```

## 状态标记

文件顶部必须标注三种状态之一：

- **草稿**：AI 生成中，尚未经过用户确认
- **待确认**：AI 已生成完整内容（brief 全文，或 PRD 全部段落），等待用户逐条/逐段过一遍
- **已确认**：用户明确确认内容准确，可以作为后续阶段的输入

## Gate 规则

**只有状态为"已确认"的需求契约，才能进入 `route-decision-recorder`、`proto-review`、`task-planning` 或 OpenSpec。**

状态还是"草稿"或"待确认"时，停在这一步，不要替用户默认确认，也不要自行推进到下一阶段。

## 移交规则

契约确认后，根据 `sdd-router` 传入的模式判断和扩展开关移交：

- **完整模式 + 需要产品原型评审** → 移交 `route-decision-recorder`，路线决策文档中引用本契约路径；路线决策确认后再进入 `proto-review`
- **完整模式 + 不需要产品原型评审** → 移交 `route-decision-recorder`，引用本契约路径
- **轻量模式** → 移交 `task-planning`，引用本契约路径（`brief` 通常已经足够）
- **用户明确要求先看原型** → 可在契约确认后直接移交 `proto-review`，`prd` 模式产出的 PRD 作为其 PRD-driven 输入

移交时传递：契约文件路径、模式（brief/prd）、已确认结论摘要、待确认问题（如有遗留）。

移交摘要中必须包含：

- `意图锁` 原文
- 哪些范围属于本轮
- 哪些内容被明确放入"不做什么"或后续迭代

下游 Skill 只能对照意图锁，不能自行改写意图锁。若发现 Decision、tasks 或 OpenSpec 需要偏离意图锁，必须回到本 Skill 修订需求契约并等待用户重新确认。

**`proto-review` 不承担 PRD 起草逻辑**——它只消费已确认的契约（brief 或 PRD）生成可视化原型评审上下文，起草工作在这个 Skill 里完成，不重复实现。

## Zimaflow State

完整模式下，如果本轮 OpenSpec change 名称已经确定，确认契约后应初始化或更新：

```text
openspec/changes/<change>/.zimaflow-state.yaml
```

写入内容遵循 `references/Design-Zimaflow-State.md`：

- `phase: contract_confirmed`
- `requirement_contract.path`
- `requirement_contract.status: confirmed`
- `requirement_contract.confirmed_at`
- `requirement_contract.intent_lock`（从契约中提取的一句话；如 state 写入工具暂不支持，至少传给下游）

如果 change 名称尚未确定，不要为了写 state 提前编造 change；把契约路径传给 `route-decision-recorder` / `task-planning`，由后续阶段在 change 建立后补写 state。

## 纠错处理

需求契约起草过程中如果用户纠正了 AI 的理解（比如"这个范围理解错了"、"这条业务规则不对"），**不建立独立的错题本**，按现有 `learn` Skill 的候选沉淀流程处理：整理成候选 lesson，等 session 收尾或用户主动确认后写入。

## 原则

- **必经的是契约，不是 PRD**：多数需求走 brief 就够，不要把 PRD 当成默认动作。
- **不要求用户先写 BRD**：优先用会议纪要或对话记录作为输入，用户口头补充作为兜底。
- **验收标准优先 GWT**：能写成 Given/When/Then 就写成三段式，方便下游直接派生测试；无行为可断言的小改动才退回一句话。
- **意图锁防漂移**：每份契约必须有一句意图锁；后续 Decision、tasks、OpenSpec 偏离时，回到契约重新确认，不在下游偷偷扩范围。
- **证据边界防越界**：遵守 ZF-GR-005，AI 可以用联想帮助搜索和追问，但范围、验收标准和业务规则必须有决策证据；AI 假设不能进入已确认范围。
- **反问最多 2 轮**：信息不足时最多问 2 轮，之后取默认值写进"假设与默认值"，用户 escape 立即收尾，绝不无限追问。
- **假设显式标注**：AI 取的默认值必须标为假设，不能伪装成用户已确认结论。
- **分段生成，逐段确认**：PRD 模式绝不一次性生成整份文档。
- **精炼投喂，不堆料**：只给和本次需求相关的精炼上下文，不全量塞历史文档。
- **已有输入不重新起草**：用户已有 PRD/brief/外部链接时，引用并确认即可，不替用户重写。
- **状态是硬 Gate**：草稿/待确认状态不能移交下一阶段，这是本 Skill 唯一的强制点（GWT、反问上限、假设默认值都是软规则，不改变这个唯一硬 gate）。
- **纠错复用 learn**：不新建平行的经验沉淀机制。

## 常见误区

| 误区 | 问题 | 正确做法 |
|------|------|---------|
| 所有需求都走 PRD 模式 | 给小改动增加不必要的负担，违背"必经契约不等于必经 PRD"的设计初衷 | 默认 brief，只有命中 PRD 信号才升级 |
