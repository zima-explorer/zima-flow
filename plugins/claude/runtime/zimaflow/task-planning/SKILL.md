# Task Planning — 任务拆解与工时估算

## 职责

你负责把一个需求描述转化为可执行的任务清单，每个任务有明确的模块归属和工时估算。

## 输入

从 sdd-router 接收：
- 项目名称、代码路径、文档路径
- 需求描述
- 所选模式（完整 / 轻量）
- 已确认的需求契约路径（brief 或 PRD；紧急热修复除外）
- 如为完整模式：本轮 `Decisions/` 文档路径，或 first slice 摘要
- 需求契约中的 `意图锁`（如调用方已提取；否则从契约文件读取）

## 执行步骤

### Step 0：需求契约 Gate

除紧急热修复外，进入任务拆解前必须确认本轮已有已确认的需求契约：

- 输入中已提供 `需求契约路径`，且状态为"已确认" → 继续 Step 1
- 用户只给了口头需求、契约仍是"草稿/待确认"、或路径缺失 → 暂停，不拆任务，交回 `sdd-router` / `requirement-contract`
- 用户明确表示这是紧急热修复 → 可先继续，但在输出中标记"紧急热修复：需求契约待补"，并在收尾时交给 `handover-manager` 记录

不要因为用户直接说"拆任务"就绕过需求契约。`task-planning` 是下游冗余 gate，用来防止直接调用本 Skill 时跳过 `sdd-router` Step 6.5。

### Step 1：理解代码现状

快速扫描项目代码结构，理解：
- 目录结构和模块划分
- 相关的现有代码（将要修改的部分）
- 技术栈（语言、框架、测试工具）

如果项目文档目录下有之前的 handover 文档，读最近 1-2 份，了解项目当前状态。

如果是**完整模式**：
- 优先读取本轮最新的 `Decisions/` 文档
- 拆任务时以其中确认的 **first slice** 为边界
- 同时读取 Decision 中的 **意图锁对照**，确保任务仍服务需求契约意图
- 如果没有 `Decisions/` 文档，暂停并提示先触发 `route-decision-recorder`

如果是**轻量模式**（含 sdd-router 的 quick 与 standard 两档）：

- **quick 档通常不需要 task-planning**：单文件低风险改动直接实现即可，不必先拆任务。只有当改动超过 3 个子步骤时，才按 Light Work Items 建立轻量台账；此时意图锁来自路由阶段的口头确认，不要求契约文件。
- **standard 档**按下列规则拆解，契约来源是最小字段 brief。

- 读取需求契约中的 `意图锁`（quick 档若无契约文件，使用路由阶段确认的一句话意图）
- 只做轻量对照：任务清单不应明显超出意图锁和"不做什么"
- 如果用户要求加入超出意图锁的新任务，标记为需求变更，回到 `requirement-contract` 重新确认或拆成后续迭代
- 如任务命中 Light Work Items 启用条件，读取 `references/Design-Light-Work-Items.md`，准备在用户确认任务清单后建立可选台账
- 如果建立 Light Work Items，可建议使用 `draft_ / ready_ / done/` 文件名前缀表达给人看的进度信号；该前缀不替代台账字段、handover 或完整模式 state

### Step 2：读取工时字典

按以下优先级读取工时基准：

1. **项目层覆盖**（可选）：`docs://project-workload-overrides.md`
2. **通用层基准**（必读）：`<zimaflow-root>/references/workload-baseline.md`

先用 `zimaflow project show --json` 解析 `docs://`；`<zimaflow-root>` 由当前宿主 adapter 提供，不能写死开发机路径。

项目层的值覆盖通用层的同名条目。

### Step 3：拆解任务

将需求拆解为独立的任务，每个任务满足：
- **单一职责**：一个任务只做一件事
- **可验证**：有明确的完成标准
- **可估算**：能匹配工时字典中的某个基准

拆解粒度指南：
- 后端：按接口/服务方法粒度拆分
- 前端：按组件/页面粒度拆分
- 数据库：DDL 变更作为独立任务
- 配置/部署：作为独立任务

完整模式下，拆解对象不是”整个宏大需求”，而是 `Decisions/` 中已经拍板的 **当前 slice**。

### Step 3.5：意图锁对照

任务输出前必须做一次轻量对照：

1. 列出本轮 `意图锁` 原文。
2. 对每个任务判断：直接服务意图 / 支撑性任务 / 超出意图。
3. 超出意图的任务不能混入本轮主清单；改列为"后续迭代 / 需求变更候选"。
4. 如果用户坚持本轮纳入超出意图的任务，暂停，回到 `requirement-contract` 修订契约并重新确认。

本步骤不新增硬门禁，不自动回退，只防止任务拆解阶段悄悄扩范围。

**硬约束：单个 tasks.md 不超过 15 项。** 超过 15 项时 AI 容易因上下文过长产生幻觉，必须拆分为多个独立变更（各自有独立的 `openspec/changes/<name>/`）。拆分策略：
1. 按模块边界拆（前端/后端/数据层各一个变更）
2. 按功能切片拆（核心流程一个变更，辅助功能一个变更）
3. 拆分后每个变更独立走 propose → apply → archive 全流程

### Step 4：估算工时

对每个任务：
1. 在工时字典中找到最匹配的基准条目
2. 根据具体情况上下浮动（说明原因）
3. 如果没有匹配的基准，给出估算并标注"无基准，需校准"

### Step 5：输出任务清单

以表格形式输出，可直接复制到项目管理系统：

```markdown
## 任务清单

| # | 任务名称 | 模块 | 工时 | 工时基准参考 | 备注 |
|---|---------|------|------|-------------|------|
| 1 | xxx | 后端 | 3h | 新增标准 CRUD 接口 | |
| 2 | xxx | 前端 | 1h | 简单 UI 组件 | |
| 3 | xxx | 测试 | 1h | 接口冒烟测试 | |

**工时合计**：5h

## 意图锁对照

- 意图锁：{从需求契约提取的一句话}
- 直接服务意图的任务：#1, #2
- 支撑性任务：#3
- 后续迭代 / 需求变更候选：{如有，列出并说明为什么不进本轮}

## Light Work Items

- 启用：是 / 否
- 判断依据：超过 3 个子步骤 / 预计跨 session / 多文件多阶段 / 有阻塞或验证证据 / 用户明确要求 / 不适用
- 建议路径：`<docs_dir>/States/YYYY-MM-DD-<task-slug>-work-items.yaml`
- 可读前缀：可选使用 `draft_ / ready_ / done/`；只表达给人看的进度信号，不替代 handover 或 state
- 说明：Light Work Items 只用于轻量模式接力，不替代 handover 或 OpenSpec tasks

**风险项**：
- （如有，列出可能导致工时膨胀的风险点）
```

### Step 6：确认并移交

等待用户确认任务清单。用户可能：
- 调整任务粒度（"把任务 2 拆细一点"）
- 修正工时（"这个按我们项目经验应该 4h"）
- 增删任务

确认后：

- **完整模式** → 提示用户进入 OpenSpec explore/propose 阶段
  > 任务清单已确认，且本轮路线决策已落知识库仓。下一步：围绕当前 first slice，在 CLI 中执行 `/opsx:explore` 讨论技术方案，然后 `/opsx:propose <名称>` 生成 spec。
  > 或者在 Cowork 中直接描述技术方案讨论需求，我来触发 OpenSpec 流程。

- **轻量模式** → 提示用户直接进入 Superpowers TDD 执行
  > 任务清单已确认。下一步：直接开始 TDD 实现，按任务顺序逐个完成。

  如果启用了 Light Work Items，按 `references/Design-Light-Work-Items.md` 生成 `work-items.yaml` 或 handover 的 `## Work Items` 表格。初始状态统一为 `todo`，执行中再更新为 `doing` / `done` / `blocked` / `skipped`；`done` 应补 `evidence_path` 和 `verify_result`，`blocked` 必须补 `blocked_reason`。如使用 `draft_ / ready_ / done/` 文件名前缀，只把它作为用户可读进度提示，不用它替代台账字段、handover 或 state。

同时，通知 handover-manager 初始化本次需求的 handover 文档（包含任务清单作为初始内容）。

## 原则

- **工时是估算不是承诺**：明确告知用户这是基于字典的参考值，实际开发中需要根据情况调整
- **不跳过确认**：任务清单必须用户确认后才能进入下一阶段
- **完整模式先有路线边界**：没有 `Decisions/` 文档时，不要替用户直接定义 first slice，更不要直接引导 `/opsx:propose`
- **任务必须对照意图锁**：任务清单不能悄悄扩展需求契约的核心目的；超出意图的内容进入后续迭代或回到契约重新确认
- **Light Work Items 可选**：只在轻量任务超过 3 个子步骤、需要跨 session、涉及多文件多阶段或有阻塞/验证证据时启用；不要给一行小改动强加台账
- **记录偏差**：如果用户修正了工时，建议同步更新工时字典（或标注为项目特有覆盖）
