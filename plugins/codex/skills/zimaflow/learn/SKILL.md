# Learn — 半自动经验沉淀

## 职责

识别开发过程中值得沉淀的经验教训，辅助整理成结构化的 lesson 条目，经用户确认后写入项目级和/或通用级经验库。跟踪同一类经验的出现频次，在达到阈值时提示进化（lesson → pattern → rule/skill）。

同时维护知识使用证据：
- 新 lesson/pattern 必须带稳定 `ID`（格式：`kf-YYYYMMDD-short-slug`）
- 新使用记录通过 `zimaflow knowledge-record` 写入用户级全局 ledger；能力根只保留兼容期历史记录
- 锚点触发规则见 `<zimaflow-root>/references/knowledge-anchor-guide.md`；具体锚点表由你自己维护，不随运行时分发
- 账本字段和淘汰规则见 `<zimaflow-root>/references/knowledge-usage-contract.md`
- **质量判断标准见 `<zimaflow-root>/references/experience-quality-criteria.md`**（三镜头判定、九类垃圾特征、事实性校验、去重否决规则、升级自检四问）

本文件负责流程（何时触发、怎么问用户、写到哪），`experience-quality-criteria.md` 负责判断（算不算经验、是不是垃圾、能不能合并、够不够格升级）。判断标准正文只在那边维护，本文件不复制。

账本只能作为证据，不能替代用户确认。`learn` 可以根据 ledger 建议更新"出现次数"、升级、降级或淘汰，但写入 lesson 正文、修改级别、回写 Skill 前必须问用户。

## 两种触发方式

### 方式 1：主动触发

用户在 session 中说"记一下这个坑"、"这个经验沉淀一下"、"learn"等，立即进入整理流程。

### 方式 2：被动触发（由 handover-manager 调用）

handover-manager 生成交接文档时，自动扫描本次 session 是否有待沉淀的经验。扫描信号：

| 信号 | 说明 |
|------|------|
| 用户纠正了 AI 的做法 | "不对，应该这样"、"别用这个，用那个" |
| 遇到报错并花时间排查 | 调试循环超过 2 轮的问题 |
| 做了技术决策并说明理由 | "选 A 不选 B，因为..." |
| 发现了框架/工具的隐蔽行为 | "原来这个 API 默认会..."、"这个配置不生效是因为..." |
| 同一类问题再次出现 | 匹配已有 lessons 中的关键词 |

扫描结果以候选列表形式呈现，**不自动写入**，等用户确认。

### 方式 3：Session 收尾候选扫描（高置信信号下主动建议）

不依赖收工触发词，而是在检测到以下**高置信信号**时，主动提出"这次有几条经验值得沉淀，要整理一下吗？"：

| 信号 | 说明 |
|------|------|
| 用户明确纠正了 AI 的关键判断 | 不是小修改，而是"你做错了方向"级别的纠正 |
| 实现发生返工 / 回滚 / 重做 | 已有代码被推倒重来，说明初始方向有误 |
| 发现旧实现却前期没有先查 | 白白绕了弯路，有明确的"应该更早做 X"的时间点 |
| 同一类问题在一次 session 内踩了两次 | 第一次没有泛化，第二次又中招 |
| 真源/runtime 或 source/dist 路径误用 | 直接改了生成副本、runtime、副本目录，后来才回写真源 |
| 公开内容被用户纠正脱敏或状态准确性 | 公司项目名、第三方名、UAT/上线状态等被用户指出必须修正 |
| 因流程缺口直接回写 Skill/规则 | 没有先沉淀 lesson，直接把经验写进了 sdd-router、reconciler、sync 规则等 |

**不触发的情况**：普通问答、正常调试、小修改、用户说"先到这"/"收工"等结束语——这些不是高置信信号，不主动扫描。

**触发后**：整理候选 lesson（≤3 条），以简短问句形式呈现，等用户确认是否沉淀。不要强制推送、不要在用户说"不用"后再追问。

## 候选筛选（呈现给用户之前）

上面三种触发方式给出的是**信号**，不是结论。信号只说明"这里可能有经验"，还要过质量判断才能成为候选。呈现给用户前按 `<zimaflow-root>/references/experience-quality-criteria.md` 走两步：

1. **三镜头判定**——这条信息 Agent 自己能不能推出来？黑话镜头（语义不可发现）、索引镜头（位置不可发现）、逻辑镜头（行为不可发现），三者都不命中就不生成候选。
2. **九类垃圾自检**——命中事实性错误、通用常识、对话摘要、一次性 case、主观偏好、缺上下文、粒度混用、不可执行、证据不足任一项的，不呈现或改写后再呈现。

其中**事实性校验是硬要求**：候选中出现具体类名、方法名、文件路径、配置项、命令时，写入前必须在代码库中 `rg` 核实存在；无法核实的标注"未核实"，不写成确定事实。错的经验比没有经验更糟——Agent 照着不存在的 API 调用会失败，且倾向于怀疑自己而不是怀疑经验。

宁可少呈现一条，也不要让用户去筛无效候选。

## 经验条目格式

每条 lesson 使用统一格式：

```markdown
## {主题标题}

- **ID**：kf-YYYYMMDD-short-slug
- **来源**：{项目名} / {日期} / {session 简述}
- **出现次数**：{N}
- **出现项目**：{项目 1, 项目 2, ...}
- **级别**：lesson | pattern | rule

### 场景

{在什么情况下遇到这个问题}

### 问题

{具体发生了什么}

### 解决方法

{怎么修的}

### 通用原则

{提炼出的可复用原则，一两句话}
```

## 写入位置

| 级别 | 写入位置 | 条件 |
|------|---------|------|
| lesson（项目级） | `<docs_dir>/lessons.md` | 默认，用户确认即写入 |
| pattern（通用级） | `ZIMAFLOW_DATA_HOME/lessons-common.md`（默认 `~/.zimaflow/data/lessons-common.md`） | 用户确认"这个跨项目通用"后写入；公开 runtime 只读兼容源内旧文件 |
| rule/skill | 项目 `CLAUDE.md` 或新建 Skill | 用户确认"封装成规则"后执行 |

## 三级进化机制

`zimaflow stale-review` 只提供 stale candidate 与每条候选最后一次 `cited` / `applied` 证据，不是完整 usage 查询接口。进化、升级与去重不能据此推断全部 `loaded` / `challenged` / 使用次数，仍以本轮可核验证据和用户确认为准。

- `loaded`：只说明读过，不能单独触发升级。
- `cited`：说明被方案、评审或 handover 引用，可作为中等强度证据。
- `applied`：说明知识改变了实现、路由或评审决策，是主要升级证据。
- `challenged`：说明知识可能过期或有误，升级前必须先复核。

### Level 1 → Level 2：lesson → pattern

当一条 lesson 满足以下任一条件时，提示用户考虑提升为 pattern：

- **出现次数 ≥ 2**（同一项目内或跨项目）
- **用户主动标注"这个是通用的"**

**提示前先过升级自检四问**（详见 `<zimaflow-root>/references/experience-quality-criteria.md`）。任一项不通过就不建议升级，或先改写再升级：

1. **When 是否过度泛化**——泛化后是否丢失了原经验的场景约束？
2. **What 是否保留了最具体、最安全、最可执行的操作建议**——有没有为了通用性把可执行步骤抽象掉？
3. **Why 是否保留了核心机制**——只剩结论没有原因，后续无法判断它是否还适用。
4. **是否引入了不受原始经验支持的新结论**——泛化过程中有没有加进对话里没有证据的推断？

提示方式：
> 这条经验"{主题}"已经在 {项目 A} 和 {项目 B} 中出现过了。
> 要同步到通用经验库（lessons-common.md）吗？

用户确认后：
1. 在 `lessons-common.md` 中写入，级别标为 `pattern`
2. 更新原项目 lessons.md 中该条目的出现次数和级别
3. 如本次确认来自 ledger 证据，在回复中列出支撑的 knowledge ID 和事件类型

### Level 2 → Level 3：pattern → rule/skill

当一条 pattern 满足以下任一条件时，提示用户考虑封装：

- **出现次数 ≥ 3**
- **pattern 描述的是一个可以被代码或规则自动执行的行为**

提示方式：
> "{主题}"已经出现 {N} 次了。你 PPT 里说的"3 次 Skills 化"——要把它封装成规则或 Skill 吗？
>
> 建议选项：
> 1. 回写到源 Skill 的约束规则中（推荐——经验直接加固触发问题的 Skill，下次不再复现）
> 2. 写入项目 CLAUDE.md 的规则段（适合项目特定约束）
> 3. 创建独立 Skill（适合跨项目通用流程）
> 4. 暂不封装，继续观察
>
> 优先选 1：实践中，一批反复出现的高频问题通过"定位源 Skill → 补约束 → 验证 → 交叉验证"被逐类消除。经验沉淀的终点应该是回写到触发问题的那个 Skill 中，而不是另建独立规则。

## 匹配已有经验的方法

每次触发时，先扫描已有经验库做去重和计数更新：

1. 读取当前项目的 `<docs_dir>/lessons.md`（如果存在）
2. 读取 `ZIMAFLOW_DATA_HOME/lessons-common.md`；不存在则说明还没有通用级经验。若私有源存在 `<zimaflow-root>/references/lessons-common.md`，它只作为低优先级、只读兼容输入；同 ID 以用户文件为准。
3. 运行 `zimaflow stale-review --json` 只评估 stale candidate 及候选最后一次 `cited` / `applied`；它不会返回完整 `loaded` / `challenged` / 全部事件列表，升级与去重不得据此虚构次数，拿不准时保留候选差异并交用户确认
4. 对候选 lesson 的主题、关键词、稳定 ID，与已有条目做相似度匹配：
   - 完全匹配（相同的错误信息、相同的 API/工具名）→ 更新出现次数
   - 相似主题（同一技术领域的类似问题）→ 先过否决规则，再提示用户确认是否为同一类
   - 无匹配 → 新建条目
5. 如果匹配到已有 ID，汇总相关 ledger 事件，区分 loaded/cited/applied/challenged，不要把 loaded 直接算成出现次数

### 去重否决规则（宁严勿宽）

核心风险不是"漏去重"，而是**误合并**——把两条本应独立的经验合成一条，边界信息永久丢失且不可逆。完整规则见 `<zimaflow-root>/references/experience-quality-criteria.md`，要点：

- 场景（When）不同不能合，即使结论看起来相似
- 主结论类型不同不能合（操作建议 / 风险规避 / 排查方法）
- 局部子机制与完整系统经验不能合
- 同一技术事实但用途不同不能合
- **禁止桥接式合并**：A~B 相关、B~C 相关，不能推出 A~C 重复

判断依据是适用场景的约束条件，不是语义相似度。拿不准时默认**保留差异**，作为两条独立候选交用户判断。

### 唯一目标判定前置

更新已有条目前，先确认历史库中是否存在"唯一最合适的目标"。如果新经验和几条历史经验都沾边、但都不属于同一条可维护经验，**默认新建**，不要强行匹配——强行匹配会污染那条历史经验的边界。

### 冲突处理

新经验与历史经验的核心结论直接冲突时，标记冲突并交用户裁决，不自动压制、不自动决断。冲突本身是有价值的信号（新旧认知不一致），不应被系统悄悄消化掉。

## 知识使用账本

当 learn 确认某条知识被复用、引用、应用或质疑时，通过 `zimaflow knowledge-record` 追加事件到用户级全局 ledger。Skill 不直接创建或编辑 JSONL，也不把新事件写回只读能力根。

最低字段由 CLI 参数表达：

```bash
zimaflow knowledge-record \
  --knowledge-id kf-YYYYMMDD-short-slug \
  --event-type applied \
  --project <项目名> --session <本轮任务简述> --stage planning \
  --trigger <触发锚点或原因> --reason <为什么读/用/质疑这条知识> \
  --json
```

写入规则：

- 由 CLI 校验字段、生成 event ID/timestamp，并在锁保护下只追加一行 JSON，不在已有事件上修改。
- 如果只是阅读，使用 `loaded`；真正影响决策才使用 `applied`。
- 如果发现旧知识不适用，使用 `challenged` 并生成 learn 候选或修订建议。
- 能力根是只读的：不要在安装好的运行时目录里写入或修改 usage 事件，全部通过 `zimaflow knowledge-record` 写全局账本。

### Ledger / Lesson 边界

ledger 是使用证据，lesson 是知识正文。两者职责不同：

| 情况 | learn 动作 |
|------|------------|
| 只读过某条知识 | 可补 `loaded` 事件；不生成 lesson 升级建议 |
| 在方案、评审或 handover 中引用 | 可补 `cited` 事件；如多次出现再提示是否升级 |
| 影响了路由、实现、验证或文档规则 | 补 `applied` 事件，并生成 learn 候选让用户确认是否补 lesson / pattern |
| 发现旧知识过期或误导 | 补 `challenged` 事件，并生成修订或淘汰候选 |
| 已直接回写 Skill / README 规则 | 仍生成 lesson 候选，说明"规则已修，补记录用于统计和复盘" |

边界要求：

- 追加 ledger 事件可以在用户确认"补记 usage"后执行；不需要同时改 lesson 正文。
- 修改 lesson 正文、出现次数、级别、deprecated 状态或 Skill 规则，必须单独获得用户确认。
- handover 的 `## Knowledge Usage` 只是交接摘要，不等于 ledger 已记录；如果缺 JSONL 事件，应作为待补项。
- 不把 `loaded` 事件计入"出现次数"，也不凭单次 `loaded` 推动 lesson → pattern。

## 淘汰候选

当用户要求清理经验库，或 session-close-reconciler 发现知识库膨胀时：

1. 按 `knowledge-usage-contract.md` 的 stale-review 规则扫描。
2. 只输出候选，不删除。
3. 让用户选择：保留、标记 deprecated、移动到归档。
4. 用户确认后再改 lesson 正文或移动文件。

## 执行步骤

### 主动触发时

1. 用户描述了一个经验/踩坑
2. 按条目格式整理（提炼场景、问题、解决方法、通用原则）
3. 过候选筛选：三镜头判定 + 九类垃圾自检 + 涉及具体标识符时做事实性校验
4. 检查是否与已有 lessons 匹配（应用去重否决规则和唯一目标判定）
5. 向用户展示整理后的内容，确认：
   - 内容是否准确
   - 写入项目级还是同时写入通用级
6. 确认后写入对应文件
7. 如确认本轮复用了已有知识，追加 ledger 事件
8. 如果达到进化阈值，先过升级自检四问，再提示进化

### 被动触发时（handover-manager 调用）

1. 扫描本次 session 的对话，识别符合信号的片段
2. 整理为候选 lesson 列表
3. 在 handover 文档末尾追加 `## 待沉淀经验` 小节：
   ```markdown
   ## 待沉淀经验

   以下经验从本次 session 中识别，待确认后沉淀：

   ### 候选 1：{主题}
   - 场景：{...}
   - 解决：{...}
   - 建议级别：lesson / pattern
   - 匹配已有：{无 / 匹配 lessons-common.md 中的 "{主题}"}

   确认沉淀？（是 / 否 / 修改后沉淀）
   ```
4. 等待用户逐条确认
5. 确认的条目写入对应文件

### Reconciler 候选触发时

当 `session-close-reconciler` 输出了 `Learn 候选`：

1. 读取候选条目，不重新发散生成无关候选。
2. 对每条候选过三镜头判定和九类垃圾自检，再检查已有 lessons 和 `lessons-common.md` 是否相似（应用去重否决规则）。
3. 检查候选是否对应已有 knowledge ID 或 ledger 事件。
4. 向用户确认是否写入，以及写入项目级还是通用级。
5. 用户确认后按统一格式写入。
6. 如果候选已经被直接回写成 Skill 规则，仍可补一条 lesson，说明"规则已修，补记录用于后续统计和复盘"。

## 原则

- **不自动写入**：任何经验必须经用户确认才写入文件。AI 的判断可能不准，宁可漏记也不要记错的。
- **过程录像不等于经验**：调试过程、失败路径、"再试一次就好了"这类内容是过程记录，不是经验。判据只有一个——被召回后 Agent 能否产生正向行为变更。
- **错的经验比没有经验更糟**：涉及具体 API / 路径 / 配置的候选必须先核实存在。Agent 照着不存在的东西操作会失败，且倾向于怀疑自己理解有误而不是怀疑经验，陷入反复重试。
- **去重宁严勿宽**：漏去重只是冗余，误合并会永久丢失边界信息且不可逆。拿不准就保留两条。
- **格式统一**：所有 lesson 遵循统一格式，确保可检索、可对比、可进化。
- **规则已修也要补记录**：直接改 Skill 能解决下次行为，但没有 lesson 就无法统计出现次数和判断是否应升级 pattern。
- **账本是证据不是裁判**：ledger 记录的是使用事实，是否升级、降级、淘汰仍由用户确认。
- **稳定 ID 优先**：引用知识时优先使用 `ID`，不要依赖标题文本。
- **进化不强制**：达到阈值时提示，但用户可以说"暂不封装"。有些经验需要更多观察。
- **已有 lessons 可导入**：如果项目已有手写的 lessons 文件（例如 `Lessons-2026-H1.md`），可以读取并标记为种子数据，后续新经验在此基础上累积和匹配。
