# Proto Review — 产品原型评审

## 职责

你负责把想法、PRD、路线决策或零散需求整理成可评审的 HTML 原型上下文。目标不是生成生产前端代码，而是在进入 OpenSpec propose 之前，让人和 Agent 对页面、状态、交互旁注、数据来源和待确认问题形成同一份可追溯依据。

## 适用场景

优先使用：

- 新页面、新一级菜单、新流程向导
- 多状态 UI：空态、异常态、处理中态、权限态、已发布/已下架等
- 涉及权限、计费、敏感信息、数据安全或用户可见状态机
- 需要产品、设计、研发、测试共同评审
- 用户明确说"缺原型"、"先看页面"、"PRD 不直观"、"只有想法没有 PRD"

通常不使用：

- 纯后端接口、批处理、CLI、内部脚本
- 小 bugfix、文案或样式微调
- 已有稳定设计稿且本轮不改变产品理解

## 前置 Gate：需求契约

除紧急热修复外，产品原型评审必须基于已确认的需求契约：

- PRD-driven：读取已确认的 PRD / brief / Decisions，并在 `review-notes.md` 的"输入来源"中引用需求契约路径
- Idea-driven：如果只有想法或零散描述，先交给 `requirement-contract` 生成并确认 brief/PRD，再进入原型评审
- 契约仍是"草稿/待确认"或路径缺失时，暂停，不生成 `prototype.html`

`proto-review` 可以帮助澄清页面和状态，但不能替代需求契约。AI 假设必须留在 review-notes 的"AI 假设/待确认问题"，不能当作已确认需求进入 OpenSpec。

## 输入模式

### PRD-driven

已有 PRD、设计文档、Decisions 或 OpenSpec 草稿时：

1. 读取需求来源，提取页面、流程、状态、业务规则、Non-goals
2. 读取项目设计规范或同类页面规范
3. 生成原型时只表达本轮范围，不吞掉后续迭代内容

### Idea-driven

只有想法、零散描述或对话上下文时：

1. 先补一份轻量需求骨架
2. 把 AI 推断内容明确标为"假设"
3. 把必须由用户拍板的内容放入"待确认问题"
4. 原型状态标记为"探索原型 / 待评审"，不得当作已确认 PRD

## 输出位置

默认输出到项目文档目录：

```text
<docs_dir>/Prototypes/YYYY-MM-DD · <需求名> prototype.html
<docs_dir>/Prototypes/YYYY-MM-DD · <需求名> review-notes.md
```

如果项目已有原型目录或 PRD 预览机制，优先沿用项目约定，但必须保证文件可被 OpenSpec proposal/design 引用。

## prototype.html 结构

推荐使用三栏结构契约：

```text
左侧：页面 / 状态导航
中间：可视化原型
右侧：PRD 旁注
```

约束：

1. 左侧导航全文件唯一，每个 section 一条入口
2. 中间原型和右侧旁注一一对应
3. 一个 section 只表达一个页面、弹窗、抽屉或关键状态
4. 不把多个业务状态塞进同一个旁注面板
5. 不为纯 hover/focus 等常规组件态单独开 section，除非它改变业务理解

### section 命名

section 命名应可被评审者和后续 Agent 直接引用：

- 应用广场 - Web 页面卡片
- 我的应用 - 空态
- 创建流程 Step 2 - 上传失败
- 管理员管理 - 已发布未上线

推荐编号方式：

| 形态 | 写法 | 用途 |
|------|------|------|
| 主页面 / 主流程 | `应用广场-01`、`创建流程-02` | 评审者按主序号顺读即可理解主流程 |
| 同页变体 | `创建流程-02-上传失败`、`详情页-01-删除确认` | 同一页面的错误态、弹窗态、确认态 |
| 空态 / 权限态 | `我的应用-01（空态）`、`管理页-02（无权限）` | 与主页面同结构，但业务含义不同 |

主序号代表新页面或新视图；变体编号代表同一页面的另一种形态。同一主序号下变体超过 3 个时，应回头判断是否需要拆成独立页面或独立 slice。

### 旁注写法

右侧旁注按视觉顺序描述：

- 页面元素
- 数据来源
- 点击行为
- 状态差异
- 权限与敏感信息
- 本期不做
- 待确认问题

规则：

- 一个可感知元素一条说明
- 用产品语言，不写代码语言
- 描述必须包含“是什么”和“点击后 / 状态变化后发生什么”
- 重复结构只在第一个 section 完整描述，后续 section 只写差异
- 改动型原型只写本次新增或改变的元素，不复述既有页面所有功能
- 失败、异常、权限不足、数据为空等业务状态要独立说明

推荐句式：

```markdown
- **{元素名}**：展示「{文案或内容}」，数据来源：{静态 / 后端 / 用户输入 / 配置}，点击后{行为}
- **{状态名}**：当{条件}时展示{状态表现}，用户可{恢复路径或下一步}
- **{按钮名}**：展示「{文案}」按钮，点击后{跳转 / 弹窗 / 提交 / 禁止原因}
```

### 评审脚手架

`data-comp` / `data-target`、PRD ↔ 原型 hover 高亮、主题 token、组件库和注入脚本暂不作为 v0.1 必选能力。

如果某次原型需要临时加入高亮脚手架，必须在 `review-notes.md` 中注明：

- 这些属性和脚本只用于评审
- 研发实现时必须剥离
- 不得进入生产前端代码

## review-notes.md 结构

```markdown
# <需求名> 原型评审说明

> 状态：探索原型 / 待评审 / 已评审
> 输入模式：PRD-driven / Idea-driven
> 原型文件：<prototype.html 路径>

## 一、输入来源

## 二、已确认结论

## 三、原型中的 AI 假设

## 四、待用户确认问题

## 五、建议进入 OpenSpec 的范围

## 六、暂不进入本期的内容

## 七、视觉依据

## 八、页面 / 状态—跳转清单

## 九、变更影响与复验

## 十、交付验收记录
```

### 视觉依据

生成前在 `review-notes.md` 记录本原型的视觉依据，三者择一或组合：

- 项目已确认的设计规范路径；
- 用户明确选择的主题 / 色板；
- 用户提供的界面截图或设计稿。

项目规范已指定默认主题时，默认主题本身就是有效依据，不额外要求用户重复选择；没有项目规范、明确选择或参考物时，暂停生成并请用户决定。不得以“AI 认为像某类产品”为依据自动选风格。

### 平台规范

原型目标平台决定可引用的规范来源和必须补的验证方式：

- **PC Web**：若项目或宿主已配置 Web 规范 / 设计系统（页面骨架、Design Token、主题、五态规则），可直接引用作为视觉依据之一，不必每次重新定义；未配置或无法确认存在这类能力时，按“视觉依据”一节的三选一自行确认，不假设某个具体外部能力一定可用。
- **App / 小程序**：Web 规范不能直接套用；必须结合目标平台自身的组件规范，并安排真实设备走查作为证据。走查记录（设备、系统版本、走查结论）写入交付验收记录的“运行环境复核结果”。
- 不把“H5 页面能在浏览器打开”当作“原生端已验证”：H5 走查结论和真机走查结论必须分别记录，不得相互替代或合并成一条。

### 页面 / 状态—跳转清单

多页、多流程或含跨 section 跳转的原型，必须在生成前建立**页面 / 状态—跳转清单**，并在评审后维护为当前版本的索引。最小字段为：

| section | 页面 / 状态 | 导航入口 | 可到达目标 / 返回路径 | 来源需求 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| `创建流程-02-上传失败` | 上传失败状态 | 创建流程 | 重试上传 / 返回创建流程-01 | PRD §3.2 上传异常 | P0 |

- `section` 必须与 HTML 左侧导航、右侧旁注中的可引用名称一致；
- 将页面、弹窗、抽屉和业务状态分别列出，不以纯 hover/focus 等常规组件态凑条目；
- `来源需求` 填写该 section 对应的 PRD / brief 章节、Decision 路径或需求契约锚点；Idea-driven 模式下填写“AI 假设”并注明待确认。需求变更时可用该字段反查所有受影响 section，评审或走查发现页面问题时也可反查其需求出处，形成双向追溯，不需要额外建索引表；
- 优先级只用于决定生成与走查顺序，不替代需求优先级或 OpenSpec task priority；
- 单页、一次性、且没有业务状态变体或页面跳转的演示可不建表，但必须在该节写明“单页豁免”及原因。

### 变更影响与复验

已生成原型的需求、旁注、导航或视觉依据发生变化时，先更新上游需求契约（如其已失效），再在 `review-notes.md` 记录本次**变更影响与复验**；不得直接全文件盲改。

1. 判定为**局部变更**或**全局变更**。局部变更仅限单一 section 的字段、文案或该 section 内部交互；导航、跨页数据结构、公共文案/组件规则、视觉依据或已确认范围变化均为全局变更。
2. 记录本次变更原因（一句话：来自哪个需求变更、Decision 或用户反馈）。
3. 列出受影响 section；局部变更至少列出一个 section，全局变更必须按页面 / 状态—跳转清单列出全部受影响 section，不能只写“全量检查”。
4. 为每个受影响 section 列出需要重做的交付验收项；导航或返回路径改变时，同时复验其来源与目标 section。
5. 单 section 内的纯文案或极小样式调整（不改变导航、状态、跳转或业务规则）适用**轻量豁免**：仍按上述步骤记录，但保留项清单与变更前快照可从简，只需在对应小节写明“轻量豁免”及原因。
6. 改动完成后更新清单、旁注和验收记录；若变更使需求契约、Decision 或 OpenSpec 失效，按 `sdd-router` 的 Change Impact 规则回到相应上游产物重新确认。

该协议只负责原型内的可追溯变更，不取代 `sdd-router` 的 P1/P2/P3 需求影响分级。

#### 保留项

全局变更、或改动会重新生成多个 section 时，先在 `review-notes.md` 列出**保留项**：已由人工修正且本轮不应被覆盖的文案、样式或交互细节（例如人工调整过的按钮文案、人工核对过的数据来源说明）。重新生成后逐条核对保留项仍在最终稿中，不得因为整篇重写而丢失人工修正。符合“轻量豁免”条件、或改动范围就是本次新增内容时可不建保留项清单，但需写明原因（“轻量豁免”或“无保留项：改动范围为本次新增”）。

#### 变更前快照

改动已存在的 `prototype.html` / `review-notes.md` 前，先复制现有文件为快照，验收失败时可直接回退。局部变更和全局变更都要建快照——局部/全局只决定第 3 步的复验范围，不决定是否需要快照：

- 命名：`prototype.snapshot-YYYY-MM-DD.html`、`review-notes.snapshot-YYYY-MM-DD.md`；同日多次变更加序号后缀（`-2`、`-3`）避免互相覆盖。
- 归档位置：与正式版本同目录下的 `_archive/` 子目录（`<docs_dir>/Prototypes/_archive/`）。
- 首次生成、尚无既有原型可快照时，在本节写明“无需快照：首次生成”，不得留空。
- 符合“轻量豁免”条件时可不建快照，写明“轻量豁免”及原因。
- 回退仅针对**原型产物**（`prototype.html` / `review-notes.md`），不回退 `proto-review/SKILL.md` 本身或上游需求契约；这两者如需回退，按各自产物已有的归档 / 版本约定处理，不由本流程代管。
- 这是文件归档约定，不引入额外的版本管理工具或系统。

### 交付验收记录

原型交付前，在 `review-notes.md` 的**交付验收记录**中逐项记录，不得省略任一栏；不要把人工判断伪装成自动通过。

**职责边界**（记录前必读）：

- AI 负责机械预检：检查项和清单字段是否齐全、可静态判断的一致性（例如跳转清单与 HTML 导航是否对得上）；
- 运行环境提供实际运行证据：页面在目标浏览器 / 设备上打开、跳转和状态是否可复现，必须由实际打开或走查产生，不能由 AI 推断代替；
- 人负责业务合理性、视觉一致性和最终是否通过的裁决；
- **AI 预检结果通过，不等于原型验收通过**：只有“人工最终裁决结果”记录为“通过”，本节才算完成。

逐项记录 `AI 预检结果` / `运行环境复核结果` / `人工最终裁决结果`（`通过 / 未通过 / 未检查`，附验证方式或证据路径），未通过项写明下一步：

| 验收项 | AI 预检结果 | 运行环境复核结果 | 人工最终裁决结果 |
| --- | --- | --- | --- |
| 原型能否在目标环境打开 | | | |
| 入口、目标页、返回路径是否连通 | | | |
| 关键业务状态是否覆盖 | | | |
| 页面说明是否与原型一致 | | | |
| 是否误做本期排除内容 | | | |

**人工评审补充**（在“人工最终裁决结果”之外，另行记录评审者与结论）：

- 版式和信息层级是否支持主流程理解；
- 跨 section 的视觉与文案基调是否一致；
- 视觉是否符合已登记依据，且没有无项目依据的 AI 默认风格。

## 评审规则

- 不把 `prototype.html` 当生产代码
- 不把 AI 假设当已确认需求
- 不把后续迭代内容混进本期 OpenSpec
- 评审后必须更新 `review-notes.md` 状态和结论
- 多页原型的页面 / 状态—跳转清单（含来源需求）、变更影响与复验（含保留项、变更前快照）、交付验收记录必须与 `prototype.html` 保持一致
- 进入 OpenSpec propose 时，proposal 或 design 必须引用原型文件和评审说明

## 移交给 zimaflow

评审完成后：

1. 如果需求范围仍未拍板，回到 `route-decision-recorder`
2. 如果 first slice 已确认，进入 OpenSpec explore/propose
3. 如果评审发现需求过大，先拆子项目或多个 slice

如果本轮 OpenSpec change 名称已确定，同时更新：

```text
openspec/changes/<change>/.zimaflow-state.yaml
```

写入内容遵循 `references/Design-Zimaflow-State.md`：

- `phase: prototype_reviewed`
- `prototype.enabled`
- `prototype.prototype_path`
- `prototype.review_notes_path`
- `prototype.status`

输出给下一阶段的最小上下文：

- 原型文件路径
- 评审说明路径
- 已确认结论
- 待确认问题
- 本期 OpenSpec 范围

## 后续参考

外部 `proto-gen` 有一套更重的 HTML 原型资产和结构契约，包括三栏布局、section 编号、PRD 旁注写法、PRD ↔ 原型双向高亮、主题 token 和组件库。当前 `proto-review` 只吸收流程思想，不安装、不复制外部资产。

需要增强原型生成能力时，先阅读 `references/proto-gen-reference.md`，再决定是否进入 v0.2 设计。
