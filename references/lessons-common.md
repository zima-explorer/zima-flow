# 通用经验库

> learn Skill 维护此文件。跨项目通用的 pattern 和 rule 沉淀在这里。
> 项目特定的 lesson 留在各项目 `<docs_dir>/lessons.md` 中。
> 级别：lesson（单项目）→ pattern（跨项目通用）→ rule（已封装为规则/Skill）
>
> 说明：以下为随发行版附带的少量种子经验，只用于展示条目格式并提供通用结论。
> 通用经验库不记录任何具体项目细节；写入 pattern 时省略或泛化来源，只保留可复用的技术原则。

## Prompt 文件引用不等于运行时加载

- **ID**：kf-20260601-prompt-runtime-loading
- **级别**：pattern

### 场景

在 Skill 或 Prompt 中引用了规则文件，期望 AI 自动遵守。

### 问题

AI "知道"规则文件存在，但执行时并没有实际读取内容，导致规则形同虚设。

### 解决方法

任何规则必须在运行时显式拼接进上下文（Read 文件 / 写入 system prompt），不能依赖"引用即加载"。

### 通用原则

对 AI 来说，没有被加载进上下文的信息等于不存在。引用 ≠ 加载，必须显式 Read。

## 高精度环节用脚本，AI 只做校验和补漏

- **ID**：kf-20260630-deterministic-gate
- **级别**：pattern

### 场景

流水线中某个环节对准确率要求极高（如从文档提取接口列表、检查改动范围、验证编译通过），错误会沿流水线逐级放大。

### 问题

完全依赖模型处理，幻觉导致遗漏或误判，且错误会逐级放大。

### 解决方法

高精度环节用确定性脚本（正则、AST 解析、编译器）处理，AI 只在脚本之后做校验和补漏。

### 通用原则

确定性工程 + 不确定性 AI = 可控流水线。对准确率要求高的环节，不要赌模型不出错，用脚本兜底。

## 新增项目文档前先读取目录命名规范

- **ID**：kf-20260711-doc-naming-readme
- **级别**：pattern

### 场景

在项目文档目录中新建 Roadmap、Design、Decision、Runbook、Report 等文档。

### 问题

AI 直接按临时任务习惯新建 `TODO-*` 之类文件名，容易违反该目录已有命名规范。

### 解决方法

新建项目文档前，先读取目标目录的 `README.md` 或同级已有文件命名模式，再决定文件名。若目录已有 `Roadmap-*`、`Design-*`、`Decision-*`、`Handoff-*` 等前缀规范，应优先沿用，不要使用临时性质的 `TODO-*` 命名。

### 通用原则

项目文档的文件名是知识库结构的一部分。新增文档前先读目录规范，比事后重命名更稳，也能减少引用同步和归档返工。

## 生成结构化输出必须给硬约束

- **ID**：kf-20260601-prompt-constraints
- **级别**：pattern

### 场景

用 LLM 生成结构化产物（SVG / HTML / JSON / 版式），期望产出稳定可用、可被下游确定性消费。

### 问题

无约束的自由生成会漂移：版式幻觉、超出画布、字段缺失、结构不一致，导致下游解析或渲染失败，且每次结果不可预期。

### 解决方法

在 prompt 中写清可枚举的硬约束（画布尺寸、允许的元素集合、禁止项、字段白名单、边界值），并在生成后用确定性脚本校验（配合 [[kf-20260630-deterministic-gate]]）。约束应是"可判定"的，而非"尽量好看"这类主观描述。

### 通用原则

生成的自由度与产出的可控性成反比。要下游能确定性消费，就必须把约束前置进 prompt，并用脚本兜底校验，而不是事后靠人肉挑错。

## 切分复杂 prompt 以降单轮复杂度

- **ID**：kf-20260601-prompt-complexity-splitting
- **级别**：pattern

### 场景

一个 prompt 同时承担多个维度的判断（如内容规划 + 版式选择 + 视觉规则 + 输出格式），生成质量不稳定。

### 问题

单轮 prompt 塞进过多正交职责时，模型注意力被稀释，某些约束被忽略，且 token 成本高、缓存命中差、难以定位是哪条规则失效。

### 解决方法

按职责把 prompt 切分成可组合的规则片段（如"基础规则"与"某类页面的专属规则"分层），由代码按当前页类型显式拼接需要的片段（配合 [[kf-20260601-prompt-runtime-loading]]，被引用的片段必须显式 load 进上下文，不能靠"引用即加载"）。分层后既能提升单轮聚焦度，也便于按需注入、提高缓存命中。

### 通用原则

降低单轮复杂度比堆砌指令更能提升生成质量。把正交规则拆分、按需组合，让每一轮只承担聚焦的判断。

## 契约先于 UI：UI 消费稳定契约而非内部实现

- **ID**：kf-20260607-contract-before-ui
- **级别**：pattern

### 场景

要为已有系统加编辑器 / 更新接口 / 渲染边界，UI 需要读写底层数据（如逐页文本编辑、payload 消费、前后端契约对接）。

### 问题

UI 直接绑定内部实现细节（内部字段结构、定位方式、脏 payload 形状）时，实现一变 UI 就碎；把 provider 的脏数据吸收进消费层，也让 owner 层缺乏诊断入口。

### 解决方法

先定义并稳定一层契约（稳定的定位句柄 / DTO / 编辑白名单 / 可编辑标记），UI 只消费这层契约，不触碰内部实现。契约的定位与状态回写策略应在动 UI 代码前先决策成文，避免编辑器状态模型被临时定位方式钉歪。

### 通用原则

UI 应该消费稳定契约，而不是绑定内部实现细节。契约先于 UI：先把定位、字段边界、回写策略定清楚，再写界面。
