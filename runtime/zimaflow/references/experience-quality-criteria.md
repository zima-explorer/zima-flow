# Experience Quality Criteria

本文件定义 `learn` 在整理、去重、升级经验条目时使用的质量判断标准。

`learn/SKILL.md` 负责流程（何时触发、怎么问用户、写到哪），本文件负责判断（一条候选算不算经验、是不是垃圾、能不能合并、够不够格升级）。两者不重复：主文档只指路，标准正文只在这里。

> 适用范围：zimaflow 个人 / 小规模场景。不引入独立评测集、不做多层 pipeline。

## 1. 根本标准：Agent 行为是否改变

一条信息算不算经验，只有一个判据：

> **被后续 session 召回后，Agent 能否产生正向的行为变更。**

如果 Agent 读到它之后做的事和没读一样，它就不是经验，无论文字写得多好。

## 2. 三镜头：判断"Agent 自己能不能推出来"

上面的标准要落地，关键在"不容易直接发现"。按 Agent 理解需求的路径分三类，命中任一类才算合格候选：

| 镜头 | 障碍本质 | 典型场景 | 信息缺口 |
|------|----------|----------|----------|
| 黑话镜头 | 语义不可发现 | 项目内部黑话、缩写、代称、内部系统别名 | 需要显式给出字面到语义的映射 |
| 索引镜头 | 位置不可发现 | 某能力/配置/入口不在直觉路径上 | 需要显式指出"去哪找"（模块、文件、关键类） |
| 逻辑镜头 | 行为不可发现 | 反直觉的工程约束、隐式机制、时序陷阱 | 常规推理会得出相反结论，需要显式说明后果 |

三镜头不是按主题（前端/后端）或重要性（高/中/低）划分——那些维度要么列不完，要么依赖主观判断。**认知障碍是客观的**：一条信息 Agent 能不能自己发现，可以判定。

三镜头都不命中 → 大概率是通用常识或过程记录，不应生成候选。

## 3. 九类垃圾特征（候选自检清单）

整理候选 lesson 时，先逐条自查。命中任一项就不呈现给用户，或改写后再呈现：

| # | 特征 | 说明 |
|---|------|------|
| 1 | 事实性错误 | 编造不存在的 API / 类 / 配置；把对话里的临时说法当成项目规则 |
| 2 | 通用常识 | 任何项目都适用，不体现本项目特异性 |
| 3 | 对话摘要 | 只复述过程，没有沉淀成可复用的判断 |
| 4 | 一次性 case | 只对当前这个任务有效，无法迁移 |
| 5 | 用户主观偏好 | 个人风格选择，不代表项目规范 |
| 6 | 缺少上下文 | 不知道对应哪个模块 / 组件 / 接口 / 场景 |
| 7 | 粒度混用 | 一条里同时塞通用规则和某个 case 的特定细节 |
| 8 | 不可执行 | 只有抽象建议，Agent 读完不知道下一步做什么 |
| 9 | 证据不足 | 对话里没有足够依据，是模型自己推断出来的 |

**为什么先列垃圾而不是先定义"好经验"**："好"很难一次定义到位，"垃圾"的特征更容易归纳，反推出的边界更稳。

### 3.1 抽取粒度：基于片段，不基于全局摘要

上面九类垃圾里，「通用常识」「对话摘要」「不可执行」这三类有一个共同的**系统性来源**：抽取时喂给模型的上下文太宽。

来源实验（一项公开报告过的对照实验）：把对话按主题切分后抽取经验，一组额外附上整个 session 的大纲，一组不附。**附大纲的那组产出了更多垃圾**——大纲会引导模型做泛化推断，偏离片段里实际发生的具体事件。

**规则**：`learn` 扫描候选时，依据应是具体的「失败 → 纠正 → 修复 → 采纳」片段，**不是整个 session 的摘要**。

- ✅ 基于片段：能看到纠正发生在哪一步、原因是什么、证据是哪几轮对话。
- ❌ 基于全局摘要：容易产出"本次开发中要注意接口兼容性"这类正确但不可执行的泛化结论。

这条与直觉相反——通常认为给模型更多上下文结果更好。在经验抽取这个特定任务上不成立：**上下文越宽，泛化倾向越强，而经验的价值恰恰在于具体**。

## 4. 事实性校验：涉及具体标识符必须核实

纯文本判断有天然局限——读起来逻辑自洽的经验，可能引用了根本不存在的方法名。

**规则**：候选 lesson 中出现具体的类名、方法名、文件路径、配置项、命令、环境变量时，写入前必须在代码库中 `rg` / `grep` 核实其真实存在。

- 核实不通过 → 按"事实性错误"处理，不呈现给用户，或改写为准确形式后再呈现。
- 无法核实（跨仓、外部服务）→ 在条目中标注"未核实"，不要写成确定事实。

**为什么必须做**：一条引用了不存在方法名的经验入库后，Agent 会照着调用导致失败，而且 Agent 更倾向怀疑自己理解有误而不是怀疑经验有问题，陷入反复重试的恶性循环。错的经验比没有经验更糟。

## 5. 去重否决规则：宁严勿宽

匹配已有经验时，核心风险不是"漏去重"，而是**误合并**——把两条本应独立的经验合成一条，边界信息永久丢失，且不可逆。

以下情况**不得合并**，即使主题相似：

| 否决规则 | 说明 |
|----------|------|
| 场景（When）不同不能合 | 即使结论看起来相似，适用场景不同就是两条经验 |
| 主结论类型不同不能合 | 操作建议 / 风险规避 / 排查方法之间不能混为一谈 |
| 局部子机制与完整系统经验不能合 | 粒度不一致，不能互相替代 |
| 同一技术事实但用途不同不能合 | 同一 API 用于性能优化和用于兼容处理，是两条经验 |
| **禁止桥接式合并** | A 与 B 有重叠、B 与 C 相关，**不能**据此推断 A 与 C 重复 |

判断依据是**适用场景的约束条件**，不是语义相似度。语义相似 ≠ 经验等价。

拿不准时的默认方向：**保留差异，不合并**，作为两条独立候选交给用户判断。

**为什么默认交用户而不是把规则做细**：来源团队用规则化 Dedup 跑了 260 条经验 4 个批次，整体 F1 只有 71.79%，且批次间波动明显——最差的一批 6 个正例只识别出 1 个，原因是"去重 prompt 对边界的敏感度在输入特征分布变化时仍有波动"。**边界判断在规则化之后仍然不稳定**，这是继续把用户确认作为兜底的实证理由，不是 zimaflow 偷懒。反过来说：在个人规模下追求自动去重的准确率，投入产出比更差。

## 6. 升级自检四问（lesson → pattern）

`learn` 的三级进化机制在提示升级前，先过一遍自检。任一项不通过就不建议升级，或先改写再升级：

1. **When 是否过度泛化**——合并后是否丢失了原经验的场景约束？
2. **What 是否保留了最具体、最安全、最可执行的操作建议**——有没有为了通用性把可执行的步骤抽象掉？
3. **Why 是否保留了核心机制**——只剩结论没有原因，后续无法判断它是否还适用。
4. **是否引入了不受原始经验支持的新结论**——泛化过程中有没有加进对话里没有证据的推断？

**唯一目标判定前置**：升级或更新前，先确认历史库中是否存在"唯一最合适的目标条目"。如果新经验和几条历史经验都沾边、但都不属于同一条可维护经验，**默认新建**，不要强行匹配到某一条上——强行匹配会污染那条历史经验的边界。

## 7. 冲突处理

当新经验与历史经验的核心结论**直接冲突**时：

- 标记为冲突，不自动压制，也不自动决断。
- 交用户裁决。

冲突意味着新旧认知不一致，这本身就是有价值的信号，不应该被系统悄悄消化掉。

## 8. 边界：本文件不做什么

- 不定义独立的 Review / Dedup / Merge 三层 pipeline——zimaflow 是 session 内半自动触发 + 用户确认，不是批量后处理。
- 不引入 Recall / Precision / Garbage Rate 形式化评测集——个人规模下投入产出比不划算。
- 不替代用户确认。本文件的所有标准都用于**减少无效候选**，不是用于自动写入。
