# sdd-router 模式边界细则

> 运行时参考。`sdd-router/SKILL.md` 只保留决策主路径，本文件承接需要时才查的细节。
> 本文件不新增规则，只承接 `sdd-router` 中移出的边界说明；语义与主文档一致，冲突时以主文档为准。

## 一、与旧命名的对应关系

下游 skill（`task-planning`、`handover-manager`、`session-close-reconciler` 等）仍在使用旧的两档命名，本轮不改接口：

```text
quick + standard  →  原「轻量模式」的两半
full              →  原「完整模式」
```

移交下游时仍传 `轻量模式` / `完整模式`；quick 与 standard 都归入轻量模式，差别在于产物轻重，不在于下游接口。

## 二、反例：看起来小但不能走 quick

| 看起来 | 实际 | 应走 |
|--------|------|------|
| "就加个字段" | 改 schema / DTO / 序列化契约 | full（ZF-GR-006 触发） |
| "就改个判断" | 动到权限、鉴权、角色校验 | full（ZF-GR-006 触发） |
| "就跑个脚本" | 批量更新或删除线上数据 | full（数据写入路径） |
| "就改个默认值" | 改变既有用户可见行为 | 至少 standard，评估兼容性 |
| "就删几行没用的代码" | 删除 ≥5 行或动到公共接口 | 至少 standard，B4 / ZF-GR-003 需要引用面排查 |
| "顺手重构一下" | 无测试安全网的重构 | 至少 standard，先建测试网 |

## 三、升级 / 降级细则

### 升级（随时可发生，不需要重新走一遍路由）

| 从 → 到 | 触发信号 |
|---------|---------|
| quick → standard | 改动超出单文件、需要多步骤、发现需要写测试才说得清 |
| standard → full | 触发 schema / 权限 / 数据写入（ZF-GR-006）、发现跨模块影响、需要记录架构决策、需要审查留痕 |
| 任意档 → full | 出现资损 / 隐私 / 合规 / 核心数据信号 |

升级时**已完成的产物不作废**：quick 的口头确认可以直接扩写成最小 brief，standard 的最小 brief 可以直接作为 full 的契约输入。不要因为升档就重写已确认内容。

### 降级（必须显式说明理由）

- `full → standard` / `standard → quick` 只在**用户明确要求**且风险判断支持时发生。
- 降级必须在路由结果的「不升完整模式理由」中写明依据。
- **不允许因为"想快点"而降级**；只允许因为"重新评估后确认风险确实低"而降级。

### 拿不准时

优先 standard，而不是 quick 或 full。quick 容易漏证据，full 容易压垮小需求。

## 四、三档常见误判

| 误判 | 纠正 |
|------|------|
| 把 quick 理解成"不检查" | quick 省掉的是**文档产物**，不是**判断动作**。风险判断、ZF-GR-005、ZF-GR-006 三档同样执行 |
| 把 standard 做成"简版 proposal + 简版 design" | standard 的特征是**不写 OpenSpec 三件套**，不是写轻一点的三件套。需要 proposal/design 才说得清 → 本来就该是 full |
| 因为需求"听起来大"就上 full | 定档看**风险与影响面**，不看需求描述的篇幅 |
| 因为项目是公司项目就一律 full | 项目协作模式影响的是扩展开关（交接/多环境/UAT 记录），不直接决定档位 |
| quick 不落盘契约 = 可以不想清楚 | 一句话说不清本轮目的，说明需求还没成型，应先澄清而不是直接动手 |
| 升档后把已写的 brief 推倒重来 | 升级不作废已有产物，扩写即可 |
| 用 hotfix 绕过流程 | P2 严重度不享受跳过待遇；P0/P1 止血后仍要补记录 |

## 五、复杂度与风险判断补充

`sdd-router` Step 5 的简表用于快速定档，以下是完整维度，需要更细致判断时查阅：

| 维度 | 小 | 中 | 大 |
|------|----|----|-----|
| 涉及模块数 | 1 个文件/函数 | 2-5 个文件 | 跨多个模块/服务 |
| 预估改动量 | < 50 行 | 50-500 行 | > 500 行 |
| 是否需要新接口/新表 | 否 | 可能 | 是 |
| 是否涉及架构决策 | 否 | 轻微 | 是 |
| 是否有旧实现可参考 | 有 → 后续流程先查 git 历史 | 无 | — |
| 是否影响既有用户路径 | 否 | 局部影响 | 影响核心路径或入口 |
| 是否涉及环境/发布差异 | 无 | 单环境配置 | 多环境、部署顺序或配置中心 |

四个风险问题：

1. 是否影响真实用户或线上系统？
2. 是否涉及数据写入、删除、接口签名变更？
3. 是否会有多人接手或协作这段代码？
4. 是否涉及资损、隐私、合规、核心数据？

路由原则不是"看起来像不像大需求"，而是**先看风险有多高，再看复杂度有多大**：

- 低风险 + 低复杂度 → quick 或 standard
- 中高复杂度 → full
- 高风险 → 至少 full；涉及资损/隐私/合规/核心数据时预留更强约束
- 拿不准 → 向上升级，宁可重一点不要事后返工

## 六、需求形态补充说明

需求形态影响**必须加载的上下文**，但不直接等同于档位：

- **问题排障不是普通 bugfix**：根因未确认前不进入 task-planning / requirement-contract / OpenSpec，先用 `superpowers:systematic-debugging` 完成复现、证据采集、根因假设和验证。排障后若只是局部实现缺陷，按 quick/standard 处理；若根因影响契约、DTO、状态机、权限、数据模型、跨系统集成或发布策略，回到对应上游阶段。
- **老项目叠加功能不自动等于 full**：低风险低复杂度可走 standard，但必须先查参考实现。
- **产品型界面/流程不自动等于 full**：一处轻微 UI 调整可 quick。存在多状态、多角色、权限、敏感信息或团队评审需求时，默认启用 `proto-review`。
- **跨系统/第三方集成不自动等于大改**，但默认风险上调一级。
- **紧急热修复优先修复**，不要在止血前强制补流程。

## 七、hotfix 严重度分档细则

> 命名区分：hotfix 严重度衡量**线上影响有多严重、能否等**；`change impact` P1/P2/P3 衡量**哪个已确认产物失效**。两套独立维度，不要混用。

| hotfix 严重度 | 判断信号 | 止血策略 |
|--------------|---------|---------|
| P0（完全不可用） | 核心功能全挂、用户完全无法使用、发布被阻断 | 先止血（回滚 / 关开关 / 降级），再定位根因；不追求一次改到位 |
| P1（部分功能炸） | 部分功能异常但主流程可用、有临时绕过 | 快速修复，跳过完整需求/设计阶段，但必须补最小记录（改了什么、为什么、影响面） |
| P2（边缘问题） | 边缘场景、低频、可延后 | 不当作热修复，退回正常路由，避免滥用 hotfix 绕过流程 |

- P0/P1 止血后，都必须在收尾时把「事故现象、根因、修复提交、影响面、验证方式」交给 `handover-manager` 记录，并按 `learn` 候选流程沉淀经验。
- P2 判定后明确告诉用户"这个不必走热修复"，回到正常路由。

## 八、不升完整模式的常见理由

路由结果必须保留"为什么不用完整模式"的解释，避免用户误以为 zimaflow 的默认动作是把所有事都流程化：

- 纯 Q&A / 代码解释 / 方案讨论：不进入开发工作流。
- 一次性脚本或临时整理：需要验证，但不需要 OpenSpec。
- 1-2 文件低风险文案、样式、配置、小 bugfix：quick 足够。
- P0/P1 hotfix：先止血或快速修复，事后补最小记录、handover 和 learn 候选。
- P2 hotfix 严重度：不当热修复，退回正常路径。
- 原型早期或需求尚未成型：先探索 / `proto-review`，不要急着 OpenSpec。
- 文档命名、目录规范、索引整理等低风险文档维护。
- 未触发多模块、schema、权限、敏感信息、跨系统、核心路径或长期协作等 full 信号。

## 九、扩展开关

扩展开关只由**项目协作模式和实际需求信号**触发，不由档位单独触发。quick 档同样可能需要交接记录。

| 扩展开关 | 触发条件 | 要求 |
|---------|---------|------|
| 无扩展 | 个人小项目，且无多人协作/多环境信号 | 不要求分支流、联调记录、UAT、测试同学记录 |
| 协作交接 | 团队协作项目，或本轮多人接手/需要跨工具交接 | handover、回归说明、关键决策记录 |
| 多环境发布 | 公司多环境项目，或本轮涉及 dev/uat/prod、配置中心、部署顺序 | 记录环境、部署范围、发布顺序、回归重点 |
| 联调/UAT 记录 | 仅公司多环境项目，且实际发生联调、测试验收或 UAT 修复 | 记录现象、根因、修复提交、部署范围、验证方式 |
| 测试阻断记录 | 仅当项目有正式测试要求但测试被环境/依赖阻断 | 记录阻断原因、替代验证、后续修复入口 |
| 产品原型评审 | 新页面/新流程/多状态 UI，或用户说"缺原型"、"先看页面"、"只有想法没有 PRD" | 触发 `proto-review`，输出 prototype.html + review-notes.md；AI 假设必须显式标注 |
